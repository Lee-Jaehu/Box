# 개발 프롬프트

당신은 신규 **Worklog** 프로젝트의 개발 담당자다. 이 폴더의 문서는 사용자와 합의한 최신 설계이며 과거 다른 업무 시스템/템플릿/도메인을 전제로 하지 않는다. 문서만 정리된 상태이며 코드 구현·실행 검증은 아직 하지 않았다. 코드가 이미 보이면 현재 상태를 조사해 문서와 차이를 확인하라.

## 먼저 읽을 파일

README.md → 08_DECISIONS.md → 01_WHITEPAPER.md → 02_UX_SPEC.md → 03_ARCHITECTURE.md → 04_DATA_MODEL.md → 05_API_SPEC.md → 06_STORAGE_OPERATIONS.md → 07_DEVELOPMENT_PLAN.md → examples/*.json.

실제 저장소의 AGENTS.md 등 적용 지침도 먼저 확인하라. 과거 대화나 별도 첨부 없이 이 묶음만으로 이어갈 수 있어야 한다. 문서에 이미 결정된 질문을 사용자에게 반복하지 말라. 정확한 라이브러리 버전과 환경 경로는 구현 기본값을 검증해서 고정하라.

## 제품 요구를 반드시 유지하라

- 브라우저에서 업무일지 작성, 개인 Windows PC FastAPI 수동 운영, 약 20명 MVP(추후 300명 확장 가능)
- 프로젝트→마일스톤→TASK. 앞의 둘은 기준정보, TASK는 일별 수행 기록으로 상태 없음.
- 프로젝트+작성자+날짜 일지 고유키. 여러 TASK/마일스톤, 재진입 이어 쓰기.
- 사용자 선택은 로그인 아님. 사번 선택, UUID 식별. 팀 하나·대표/참여자 구분.
- 단발성 간편 입력·마일스톤 빠른 추가·일반/수시 업무 항목.
- Word/Notion식 마우스 편집·표·체크리스트·공용/자유 간트. 문서 JSON 원본.
- 이미지 TASK 바인딩·상세 설명 필수, 문서 첨부 20MB.
- 정량/정성 성과 프리셋·정량 KPI 선택 연결. 의미 없는 합산/자동 실적 덮어쓰기 금지.
- To-Do/Issue는 프로젝트 트래커. 일지 등록 후 현재 상태와 과거 snapshot 분리.
- Issue→대응 To-Do 선택, 일별 TASK 상시 연결 안 함. 완료/해결 시 한 줄 결과로 선택 TASK 생성, 원자적 저장.
- 일지 전체 저장·IndexedDB 초안·revision 충돌·멱등성·휴지통·다시 열기.
- SQLite가 원본, data/json 프로젝트/date 사본 단방향 자동 생성. 작업 예약은 DB에 내구적으로 저장.
- xlsx/csv 명단 검증 preview, 오류 시 전량 적용 중단.
- DB/첨부 backup 최근 성공 14개, 삭제 자동 purge 없음.
- 실행.bat 탐색 순서 Conda→embedded→venv. 자동 부팅/서비스/자동 재시작 없음.
- Node.js는 개발 빌드용. 배포된 FastAPI는 빌드 자산을 제공하며 운영 Node 불필요.
- 요약 agent/PPT 구현, 300명 확장, 인증/SSO는 MVP 밖이다.

## 이번 작업 지시

1. 작업 폴더와 도구/환경을 조사하고 현재 코드 유무를 보고하라. 데이터나 다른 파일을 덮어쓰지 말라.
2. 짧은 실행 계획을 세우고 즉시 P0 핵심 편집 시제품을 구현·검증하라. 계획만 제시하고 멈추지 말라.
3. 시제품에서 문서 JSON 왕복과 간트·이미지 메타데이터를 검증하고, 결과를 반영해 실제 schemas/migrations/API를 작성하라.
4. P1부터 작동하는 기능 단위로 구현을 이어가라. 규모 때문에 나눌 경우 완료 범위와 정확한 다음 작업을 원장/README에 남겨라.
5. 중요한 위험 위주 테스트를 작성하라: 일지 unique/revision, 완료+TASK 원자성, 멱등 재전송, export 재시작/수정 race, 이미지 필수 설명, import all-or-nothing, backup restore.
6. UI만 만들고 persistence가 동작하는 것처럼 표시하거나, 하드코딩 demo를 실제 저장 결과처럼 보고하지 말라.
7. 현재 환경이 Linux라면 Windows 실행 검증은 별도 미실시로 표시하고, 실제 Windows smoke checklist와 재현 절차를 제공하라.
8. 이미 합의된 기능의 재승인을 요구하지 말고, 대안이 필요한 기술 제약만 근거와 함께 설명하라. 제품 범위를 확대하지 말라.

## 코드/문서 관리

API/Service/Repository, Editor/Gantt adapter를 분리하되 과도한 범용 프레임워크를 만들지 말라. SQLAlchemy transaction 범위를 짧게 유지하고 외부 파일 처리와 분리하라. 데이터와 config를 소스 업데이트로 지우지 말라. 런타임/사용자 데이터/빌드 캐시/첨부를 Git에 잘못 포함하지 말라.

AGENTS의 지침과 사용자 권한을 준수하라. 서버를 임의 외부 공개하거나 방화벽을 자동 변경하지 말라. 업무 데이터를 외부 AI에 전송하는 기능은 이번 범위에 없다.

작업 후 실제 변경·실행한 테스트·결과·미실시 검증·남은 작업·migration 필요성을 보고하고 README/결정원장/개발계획을 갱신하라. 아직 없는 실행기나 미검증 라이브러리를 완료됐다고 쓰지 말라.
