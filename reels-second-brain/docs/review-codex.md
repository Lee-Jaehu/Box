# Codex 교차 리뷰

지정된 8개 파일을 PRD D15, 8.1, 8.2, 10장 기준으로 읽기 전용 검토했다. 아래는 구체적인 실패 경로가 있는 사항이다. 심각도 blocking은 운영 전 수정이 필요한 정확성 문제를 뜻한다.

## 1. 임대 소유권 확인 없이 이전 실행이 작업 상태를 덮어씀

- 위치: `src/rsb/jobs.py:34`, `src/rsb/jobs.py:46`, `src/rsb/jobs.py:53`, `src/rsb/worker.py:173`
- 심각도: blocking
- 시나리오: 워커 A의 OCR 등이 lease보다 오래 실행되면 워커 B가 같은 작업을 다시 claim한다. heartbeat가 없고 succeed/fail이 id만 조건으로 갱신하므로, A가 뒤늦게 실패하면 B가 성공시킨 작업을 queued로 되돌릴 수 있다. 반대로 A가 성공하면 실행 중인 B의 작업을 완료 처리한다. 두 실행은 같은 임시 작업 디렉터리도 사용하여 한쪽 정리가 다른 쪽 파일을 삭제할 수 있다.
- 제안 수정: claim마다 고유 실행 토큰을 발급하고 heartbeat로 임대를 연장한다. 완료·실패 및 처리 결과 저장은 현재 실행 토큰 소유권을 확인한 트랜잭션에서 수행하고, 임시 경로도 실행별로 분리한다. 소유권을 잃은 실행은 결과를 반영하지 않는다.

## 2. 답장 전송 성공 후 장애가 나면 같은 답장이 재발송됨

- 위치: `src/rsb/worker.py:154`, `src/rsb/worker.py:174`, `src/rsb/worker.py:189`
- 심각도: blocking
- 시나리오: Send API가 메시지를 전달한 직후 워커가 종료되거나, 전송 후 DB 커밋이 실패하면 jobs에는 running 상태가 남는다. lease 만료 후 다시 실행하면 같은 답장을 또 보낸다. 전송은 성공했지만 응답만 유실된 경우에도 재시도로 중복된다. enqueue의 idempotency_key는 같은 job의 재실행을 막지 못한다.
- 제안 수정: 발송 시도·성공·결과 불명 상태를 영구 기록하고 결과 불명 발송은 무조건 자동 재전송하지 않도록 한다. 공급자가 멱등 발송 키를 지원하는지 확인하고, 지원하지 않으면 결과 대조 또는 수동 확인 경로를 마련한다. 외부 전송과 DB 커밋을 단순히 하나의 트랜잭션으로 묶는 것만으로는 해결되지 않는다.

## 3. DB 수신 시각이 24시간 응답 창의 시작으로 사용됨

- 위치: `src/rsb/worker.py:150`, `migrations/001_stage1.sql:11`, `src/rsb/instagram.py:56`
- 심각도: blocking
- 시나리오: 서버 또는 DB 장애로 Meta의 최초 웹훅 처리가 실패하고 실제 메시지 발생 25시간 뒤 재전달이 처음 저장되면 received_at은 현재 시각이 된다. 워커는 응답 창 안이라고 판단하여 24시간이 지난 메시지에 자동 답장을 시도한다. 현재 파서는 이벤트 timestamp를 별도 검증·보존하지 않고 창 계산에도 쓰지 않는다.
- 제안 수정: 원본 메시지의 발생 시각을 파싱·검증하여 저장하고 이를 기준으로 응답 가능 여부를 계산한다. 시각이 없거나 신뢰할 수 없으면 자동 답장을 보수적으로 차단한다. 이후 대화의 최신 사용자 메시지로 창을 연장하려면 해당 시각을 별도로 추적한다.

## 4. video ID가 없는 동일 릴스는 중복 제거되지 않음

- 위치: `src/rsb/intake.py:48`, `src/rsb/intake.py:59`, `migrations/001_stage1.sql:16`
- 심각도: minor
- 시나리오: 지원 첨부에 URL은 있지만 video ID가 없을 때, 사용자가 같은 릴스를 다른 message_id로 두 번 보내면 reels가 두 개 생성된다. 각 reel_id로 fetch·OCR·전사가 별도 등록되어 동일 영상에 중복 작업과 비용이 발생한다. URL만 있는 첨부는 현재 파서가 정상 접수하는 입력이다.
- 제안 수정: 검증 가능한 Instagram 릴스 URL에서는 안정적인 콘텐츠 식별자를 추출하여 고유 키로 사용하고, ID가 없는 경우에도 안전하게 정규화한 동일 URL에 대한 중복 방지 키를 둔다. intakes는 각 접수 기록으로 유지하되 처리 작업은 기존 reel을 재사용한다.

## 그 외 검토 결과와 한계

- 정상 입력의 웹훅 경로는 이벤트·접수·작업을 같은 메시지별 트랜잭션에 저장하고 연결 컨텍스트 커밋 후 200을 반환한다. 저장 예외는 503이다. message_id 중복 시 후속 처리를 하지 않는다.
- 카카오 state는 일회성 삭제와 만료 검사를 수행한다. 사용자 ID 검증, Fernet 암호화, 갱신 행 잠금, 새 refresh token 미발급 시 기존 암호문 유지가 구현되어 있다. 검토한 코드에서 확정할 수 있는 추가 SQL 주입 또는 직접적인 토큰 로그 노출 문제는 찾지 못했다.
- 코드 정적 검토 결과이며 실계정 연동 성공을 의미하지 않는다. 위 파일은 수정하지 않았다.
