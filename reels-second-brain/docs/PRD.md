# 릴스 세컨브레인 기획안

Oct 18, 2026 · @재후

## 1. 개요

릴스를 전용 인스타 계정에 DM으로 보내기만 하면, 영상 속 정보를 읽고 부족한 내용은 근거와 함께 보강한다. 쌓인 정보는 질문으로 찾고, 주간 다이제스트로 다시 떠올린다. 이번 범위는 재후 1인용 PoC다.

**핵심 약속:** 정리하지 말고 보내두세요. 필요할 때 찾아드릴게요.

### 해결할 문제

| 문제 | 현재 상황 | 이번 PoC의 대응 |
| --- | --- | --- |
| 찾기 어려움 | 저장이 많아지면 어디에 무엇이 있는지 모름 | 질문형 검색 (DM·모바일 웹) |
| 존재를 잊음 | 필요한 순간에 저장한 사실 자체를 떠올리지 못함 | 주간 다이제스트(알림 채널은 D8 결정 대기) |
| 정보 부족 | 댓글·팔로우 유도형 릴스는 핵심 정보를 DM·노션으로 미룸 | 외부 근거 기반 보강, 출처 구분 표시 |

### 목표

- 릴스 1개를 보낸 뒤 추가 입력 없이 검색 가능한 정보 카드가 생성된다.
- 화면 자막과 음성에만 있는 팁까지 카드에 담긴다.
- 2\~3주 실사용에서 저장한 정보를 실제로 다시 찾아 쓴다.

서비스화(다른 사용자 대상)는 PoC 결과를 보고 별도로 판단한다. 이 문서의 허용 범위(비공식 다운로드 등)를 서비스 운영으로 확대 해석하지 않는다.

**현재 착수 범위는 1단계 기술 검증뿐이다.** 웹훅 수신, 영구 접수 기록, 릴스 5개의 영상 확보·전사·화면 추출, 카카오 동작 확인까지만 구현한다. 2단계 이후는 1단계 결과로 이 문서를 고친 뒤 시작한다.

**표기 규칙:** \[확정\]은 재후와 합의한 결정, \[권장\]은 구현 중 바꿀 수 있는 안, \[가설\]은 실제 확인 전 외부 API 동작이다. \[가설\]을 확정 계약처럼 코드로 굳히지 않는다.

## 4. 사용자 흐름

재후가 하는 행동은 '보내기'와 '묻기' 두 가지뿐이다. 분류, 태그, 요약 확인은 요구하지 않는다.

| 순간 | 재후의 행동 | 시스템의 응답 |
| --- | --- | --- |
| 유용한 릴스 발견 | 공유 → 세컨브레인 계정 선택 | 영구 저장 후 "접수했어요" 답장, 분석 작업 등록 |
| 분석 완료 | 없음 | 조용히 팁 카드 생성·검색 등록. 알림 없음 |
| 일부만 분석됨 | 없음 | 음성 성공·화면 실패 같은 단계별 상태를 보관함에 표시 |
| 분석 실패 | 모바일 웹에서 재시도 | 실패 이유와 재시도 버튼 제공 |
| 정보가 필요함 | DM에 평소 말투로 질문 | 바로 쓸 답 → 적용 조건 → 근거·원본 링크. 저장 지식에 없으면 "저장한 정보에서 찾지 못했어요" |
| 자세히 보고 싶음 | 모바일 웹 열기 | 검색창, 최근 카드, 출처·검증 상태별 근거, 중복 후보 |
| 매주 정해진 시간 | 없음 | D8 채널로 팁 최대 3개, 각 팁의 활용 상황, 선정 이유, 상세 링크 |
| 다이제스트 확인 | 유용함 / 나중에 / 관심 없음 선택(모바일 웹) | 해당 다이제스트 기준으로 반응 기록, 다음 선정에 반영 |
| 같은 릴스를 다시 보냄 | 없음 | 기존 분석 재사용, 접수 기록만 추가 |

### 상태 표시 원칙

- 상태는 시스템이 기록하고, 화면에서는 조합해 보여준다: 수집 / 음성·화면·캡션별 추출 / 구조화·보강·색인 / 주장별 검증. 모델이 처리 완료를 선언하지 않는다.
- 내용을 읽지 못한 릴스를 정리된 지식처럼 보여주지 않는다.
- 다이제스트의 선정 이유는 선정 규칙에서 나온 사실만 쓴다(예: "3주 전 '나중에'를 누른 팁"). "지금 필요할 것 같아요" 같은 추정 문구는 쓰지 않는다.
- 가격·지원금·앱 사용법처럼 바뀌는 정보는 확인 날짜를 함께 보여주고, 실제로 쓰기 전 재확인을 안내한다.

### 질문 예시

- "전에 받은 엑셀 자동화 팁 찾아줘."
- "아이들이랑 갈 만한 곳 뭐 저장했지?"
- "내가 모아둔 영상 제작 도구 비교해줘."
- "회사 자료를 외부에 올리지 않고 보고서 시간을 줄일 방법 있어?" (주제가 아니라 상황으로 묻는 질문)

## 5. 시스템 아키텍처

서버 하나가 웹훅·검색 API·스케줄러를 맡고, 무거운 영상 분석은 별도 워커가 비동기로 처리한다. 재후가 보는 곳은 인스타 DM, 모바일 웹, 카톡 세 곳뿐이다.

**텍스트 버전(마크다운 내보내기에서는 그림이 빠지므로 이 목록을 기준으로 한다):**

1. 재후 본계정 → 세컨브레인 계정으로 릴스·질문 DM
2. Meta 웹훅 → 웹훅 서버: 서명 검증, 수신 계정·송신자 확인, 에코 제외 → webhook\_events·jobs에 영구 저장 → 200 응답
3. 릴스 작업 → 분석 워커: 영상 확보 → 음성 전사·화면 추출 → 팁 분해·근거 연결 → 보강·검증 → 색인 → PostgreSQL
4. 질문 → 검색 API: 벡터·키워드 검색 → 근거 있는 답변 → Send API로 DM 답장(24시간 창 안)
5. 모바일 웹 ↔ 검색 API: 검색, 카드 상세, 처리 상태, 재시도, 다이제스트 반응(feedback)
6. 다이제스트 스케줄러: 선정 규칙으로 최대 3개 → D8 채널로 발송(카톡 나에게 보내기는 보관용)

### 권장 기술 스택

| 구성 | \[권장\]안 | 비고 |
| --- | --- | --- |
| 서버 | Python + FastAPI | 웹훅, API, 카카오 OAuth를 한 프로세스로 |
| 작업 큐 | PostgreSQL jobs 테이블 + 워커(SELECT … FOR UPDATE SKIP LOCKED) | 별도 Redis 없이 영구 큐. 프로세스 안 비동기 작업을 큐로 쓰지 않음(D15) |
| 호스팅 | Render·Fly.io 같은 컨테이너 호스팅, 또는 집 PC + Cloudflare Tunnel | ffmpeg·yt-dlp를 실행해야 하므로 Cloudflare Workers 같은 서버리스는 부적합 |
| DB | PostgreSQL + pgvector | Supabase 무료 플랜 등 |
| 전사 | Whisper (API 또는 로컬 faster-whisper) | 한국어 정확도 1단계에서 확인 |
| OCR·구조화·보강 | 비전 지원 LLM + 웹 검색 | 한글 자막은 전통 OCR보다 비전 LLM이 유리 |
| 임베딩 | 처음엔 pg\_trgm 키워드 검색, 필요 시 임베딩 모델 추가(D17) | 차원은 6장 스키마와 맞춤 |
| 스케줄 | 호스팅 크론 | Asia/Seoul 기준, 중복 발송 방지(8.4) |

앞선 검토에서 웹훅 호스팅으로 Cloudflare Workers를 언급했지만, 영상 처리 요구 때문에 위 권장안으로 정정한다. 스택은 권장안이며 Claude Code·Codex 작업 중 바꿀 수 있다.

### 참고한 설계 패턴: 세컨브레인 영상과 LLM 위키

커리어해커 알렉스 영상(2026년 5월, 67분)의 한국어 자막 전체를 분석했다. 영상은 두 부분이다. (1) 알렉스가 메타에서 만든 세컨브레인 시연: 원자 단위 노트, 타입 있는 그래프(온톨로지), Claude Code가 소스를 정제해 기존 지식과 연결, 출처가 붙은 질의응답, 실제 질문으로 매일 하는 평가. (2) 게스트의 유튜브 대본 11개로 Karpathy LLM 위키 + Obsidian 세컨브레인을 즉석에서 만드는 시연.

| 영상의 요소 | 영상 내용 | 세컨브레인 적용 |
| --- | --- | --- |
| 원자 단위 노트 | 생각을 잘게 쪼개 하나씩 저장 | 이미 반영(D11, 팁 단위) |
| 타입 있는 그래프(온톨로지) | 노드 유형(생각·통찰·절차·사건·주장)과 관계 유형(지지·확장·유사·반박)을 정의 | **적용.** 팁에 kind(절차·도구·장소·개념·주장)를 추가해 필터에 쓴다. 관계는 기존 4종(보완·대안·중복·상충)과 근거의 지지·반박으로 충분 |
| 출처 표시 | 답변마다 출처를 붙여 직접 검증 가능, 환각 억제 | 이미 반영(D9, evidence) |
| 실제 질문 기반 평가 | 들어온 질문의 답을 매일 보고 "이렇게 답했어야"로 고침, 평가셋 30개 이상 | **적용.** 8.5 질문 품질 개선 루프 |
| LLM 위키 | 청킹·임베딩 없이 색인을 읽고 에이전트가 찾아감. 위키는 원문 전체를 읽지 않게 해 주는 캐시 | **적용.** D17: 수백 개 규모에서는 키워드·색인 검색부터 |
| 대규모에서 필터 검색의 한계 | 태그 검색 결과가 수만 개면 쓸모없음 → 임베딩·에이전트 필요 | D17의 임베딩 도입 조건으로 반영 |
| Obsidian 그래프 뷰 | 둘러보기·태그 필터에는 좋지만, 실제 활용은 에이전트 질의. CLI로 그래프 필터는 불가 | **제외 유지(D10).** 대신 "내가 뭘 모아뒀지" 개요 질문과 답변 아래 연결 팁 목록 |
| 검색하면 관련 지식이 함께 보이는 UI | 알렉스 시스템의 핵심 화면 | **적용(경량).** 답변 아래 근거 팁과 연결 팁 표시(8.3) |
| 모델과 독립된 기억 | 모델을 바꿔도 같은 뇌를 연결, MCP·CLI로 어디서든 사용 | 이미 반영(PostgreSQL). MCP 노출은 8.6 선택 기능 |
| 문체·보이스 학습, 사칭 위험 | 본인 콘텐츠 제작용 | 해당 없음 |

두 사람의 결론은 "그래프는 보조, 핵심은 에이전트 질의"였고, 이는 D10과 같다. 알렉스 개인 시스템의 구체 구현(임베딩·증류 방식)은 영상에서 공개되지 않았고, LLM 위키 시연은 대본 11개짜리 소규모라 대규모 성능 근거는 아니다.

## 6. 데이터 모델

지식의 단위는 개별 팁(D11)이고, 팁 안의 주장마다 출처와 검증 상태를 따로 가진다(D9). 접수와 처리는 영구 기록으로 남겨 재전달·서버 종료·부분 실패에서도 이어서 처리한다(D15). 1단계에서 실제로 만드는 테이블은 굵게 표시했다. 나머지는 2단계 진입 전 실제 페이로드를 보고 확정한다.

### 접수·처리 계층

| 테이블 | 역할 | 핵심 필드 |
| --- | --- | --- |
| **webhook\_events** | 웹훅 원본. 메시지 ID로 중복 차단 | message\_id(고유), sender\_id, recipient\_id, kind, payload, received\_at |
| **jobs** | 영구 작업 큐 | kind, reel\_id, stage, status(queued / running / succeeded / failed), attempts, lease\_until, last\_error, idempotency\_key |
| **reels** | 원재료. 릴스 1개 = 1행 | ig\_video\_id(고유), url, caption, fetch\_status, video\_path, video\_delete\_after |
| **intakes** | 접수 기록. 실제 재공유는 새 행 | reel\_id, event\_id, source(dm / export), note(함께 온 텍스트), received\_at |
| **extractions** | 매체별 추출과 상태 | reel\_id, medium(audio / screen / caption), status, text, segments(시간대·위치), extractor\_version |
| **processing\_runs** | 재처리 이력·비용 | reel\_id, stage, model, prompt\_version, started\_at, finished\_at, cost\_estimate |

### 지식 계층 (2단계)

| 테이블 | 역할 | 핵심 필드 |
| --- | --- | --- |
| tips | 지식 카드 | title, kind(절차·도구·장소·개념·주장), problem, use\_when, conditions(지역·버전·요금제·대상·시점), gaps, is\_lure, actionable, verified\_at, recheck\_at, human\_edited, embedding(D17 조건 충족 시) |
| tip\_steps | 실행 단계 | tip\_id, position, text, claim\_ids |
| claims | 개별 주장 | tip\_id, text, origin, verification, importance(key / normal) |
| evidence | 주장의 근거 | claim\_id, source\_kind(audio / screen / caption / web / user), reel\_id, locator, excerpt, url, checked\_at, stance(supports / refutes) |
| tip\_relations | 중복 후보 등 관계 | from\_tip, to\_tip, type, status(candidate / accepted / rejected), judged\_by(model / human) |
| digests, digest\_items | 발송 단위와 항목 | scheduled\_for, status(pending / sent / failed / unknown), tip\_id, reason\_code |
| feedback | 다이제스트 반응 | digest\_id, tip\_id, value(useful / later / not\_interested), at |
| kakao\_tokens | 토큰 | access\_token, refresh\_token, expires\_at, refresh\_expires\_at(암호화 저장) |
| question\_log | 질문·답변 기록과 피드백(8.5) | question, answer, used\_tip\_ids, used\_claim\_ids, feedback, expected\_answer, failure\_type(검색 누락 / 답변 오류 / 지식 없음), in\_eval\_set |

### 출처와 검증 (D9)

| 축 | 값 | 의미 |
| --- | --- | --- |
| origin | original / external / user\_provided / ai\_alternative | 어디에서 나왔나 |
| verification | unverified / supported / contradicted / unverifiable | 사실로 확인됐나 |
| gaps(팁 필드) | 빠진 정보 목록과 상태(조사 전 / 보완됨 / 확보 불가) | 무엇이 부족한가. claims의 출처 값으로 쓰지 않음 |

```sql
-- 1단계 테이블 [권장] 초안 (PostgreSQL)
CREATE TABLE webhook_events (
  id BIGSERIAL PRIMARY KEY,
  message_id TEXT UNIQUE NOT NULL,     -- 재전달 중복 차단
  sender_id TEXT NOT NULL,
  recipient_id TEXT NOT NULL,
  kind TEXT NOT NULL,                  -- reel / text / unsupported / ignored
  payload JSONB NOT NULL,
  received_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE jobs (
  id BIGSERIAL PRIMARY KEY,
  kind TEXT NOT NULL,                  -- fetch / transcribe / ocr / reply
  reel_id BIGINT,
  status TEXT NOT NULL DEFAULT 'queued',
  attempts INT NOT NULL DEFAULT 0,
  lease_until TIMESTAMPTZ,             -- 워커가 죽으면 만료 후 재수거
  last_error TEXT,
  idempotency_key TEXT UNIQUE,         -- 같은 작업 중복 등록 방지
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE reels (
  id BIGSERIAL PRIMARY KEY,
  ig_video_id TEXT UNIQUE,
  url TEXT NOT NULL,
  caption TEXT,
  fetch_status TEXT NOT NULL DEFAULT 'pending',  -- pending / fetched / failed
  fetch_error TEXT,
  video_path TEXT,
  video_delete_after TIMESTAMPTZ       -- 검증 채점 후 삭제
);

CREATE TABLE intakes (
  id BIGSERIAL PRIMARY KEY,
  reel_id BIGINT REFERENCES reels(id),
  event_id BIGINT REFERENCES webhook_events(id),
  source TEXT NOT NULL CHECK (source IN ('dm','export')),
  note TEXT,
  received_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE extractions (
  id BIGSERIAL PRIMARY KEY,
  reel_id BIGINT REFERENCES reels(id),
  medium TEXT NOT NULL CHECK (medium IN ('audio','screen','caption')),
  status TEXT NOT NULL,                -- pending / succeeded / failed / empty
  text TEXT,
  segments JSONB,                      -- [{start, end, text}] 또는 [{frame_ts, text}]
  extractor_version TEXT,
  UNIQUE (reel_id, medium, extractor_version)
);
```

지식 계층 DDL은 1단계 결과(실제 추출 품질과 페이로드)를 반영해 2단계 착수 전에 확정한다. 사람이 고친 필드는 human\_edited에 기록해 자동 재처리가 덮어쓰지 않게 한다.

## 7. 분석·보강 파이프라인

릴스 1개는 확보 → 추출 → 팁 분해 → 판별 → 보강·검증 → 후보 연결·색인 6단계를 거친다. 1단계는 앞의 두 단계만 만든다. 각 단계는 jobs로 나뉘어 실패한 단계부터 다시 시작하고, 상태는 시스템이 기록한다.

1. **영상 확보 (1단계):** 웹훅 URL이 영상 파일이면 바로 받고, 게시물 링크면 yt-dlp로 받는다. 결과는 reels.fetch\_status와 이유로 남긴다.
2. **추출 (1단계):** 매체별로 extractions에 상태를 따로 남긴다.
   - 음성: ffmpeg로 오디오 분리 → Whisper 전사(구간 시각 포함)
   - 화면 글자: 장면 전환 또는 1초 간격 프레임 → 중복 프레임 제거 → 비전 LLM 판독(프레임 시각 포함)
   - 캡션: 웹훅 페이로드 또는 페이지 메타데이터(시간대 없음, 텍스트 위치로 참조)
3. **팁 분해 (2단계):** LLM이 팁과 주장을 만들고, 주장마다 근거 발췌(excerpt)와 위치(locator)를 붙인다. 실행 단계는 사용한 claim id를 참조한다.
4. **판별 (2단계):** 유도 여부(is\_lure) × 실행 가능성(actionable)으로 gaps를 정하고, 숫자·가격·조건·절차가 담긴 주장을 핵심 주장(key)으로 표시한다.
5. **보강·검증 (2단계):** gaps를 조사해 채우고, 핵심 주장은 원본에서 나왔더라도 외부 근거로 검증한다. 근거가 주장을 반박하면 verification=contradicted로 두고 카드에 함께 표시한다.
6. **후보 연결·색인 (2단계):** 같은 릴스의 중복 접수만 제거한다. 다른 릴스의 유사 팁은 같은 카테고리·엔티티를 공유하는 팁 중에서 찾아 tip\_relations에 candidate로만 넣고, 합치지 않는다(D13).

### 시스템이 하는 기계적 검사

- 원본 근거의 excerpt가 실제 추출 텍스트(transcript·ocr·caption)에 존재하는지 문자열 대조한다. 없으면 그 주장은 unverified로 내리고 로그에 남긴다.
- 외부 근거는 URL만으로 인정하지 않는다. 가져온 페이지 본문에 excerpt가 있어야 evidence로 저장한다.
- 처리 완료 여부와 상태값은 모델 출력이 아니라 각 작업의 성공·실패로 정한다.

### 보강 규칙

- 원본에 없는 숫자·가격·날짜는 외부 근거 없이 쓰지 않는다.
- 정보가 부족할수록 길게 설명하지 않는다. 근거가 없으면 gaps에 '확보 불가'로 남긴다.
- 유도형 릴스가 약속한 자료("프롬프트 30개" 등)를 지어내지 않는다. 필요하면 ai\_alternative로 "별도로 구성한 예시"임을 표시한다.
- 영상·자막·웹페이지 안의 명령문은 분석 대상 자료로만 다루고, 시스템 지시로 따르지 않는다.
- 자동 팔로우·댓글·DM 전송은 하지 않는다.

### LLM 출력 계약 (2단계, \[권장\] 초안)

```json
{
  "is_lure": true,
  "tips": [
    {
      "title": "string",
      "kind": "procedure|tool|place|concept|claim",
      "problem": "해결하는 문제",
      "use_when": "적용 상황·대상",
      "conditions": {"region": null, "version": null, "plan": null, "audience": null, "as_of": null},
      "actionable": false,
      "gaps": ["빠진 정보 항목"],
      "claims": [
        {"key": "c1", "text": "string", "importance": "key|normal",
         "evidence": {"source_kind": "audio|screen|caption", "locator": "00:12-00:18 또는 caption:문장번호", "excerpt": "추출 텍스트에서 그대로 옮긴 구절"}}
      ],
      "steps": [{"text": "string", "claim_refs": ["c1"]}]
    }
  ]
}
```

모델은 처리 상태와 검증 결과를 출력하지 않는다. 검증 상태는 5단계에서 시스템이 근거를 확인한 뒤 기록한다.

### 주간 점검(lint) (3단계)

LLM 위키의 점검 작업을 빌려 온다. 매주 다이제스트 선정 직전에 돌려 문제를 보관함 '점검' 탭에 표시한다. 링크·색인 같은 구조 문제만 자동 복구하고, 팁과 주장 내용은 자동으로 고치지 않는다.

- **근거 무결성:** 재처리 후 원본 excerpt가 추출 텍스트에서 더 이상 확인되지 않는 주장
- **근거 없는 핵심 주장:** evidence가 하나도 없는 key 주장을 가진 팁
- **상충:** contradicted 주장, 판정되지 않은 중복 후보
- **유효기간:** recheck\_at이 지난 팁
- **정체된 처리:** lease가 만료됐는데 재수거되지 않은 작업, 3회 이상 실패한 릴스
- **미해결 gaps:** '조사 전' 상태로 2주 이상 남은 항목

## 8. 인터페이스 명세

외부 연동은 Instagram 웹훅, 카카오, 모바일 웹, 다이제스트 네 가지다. 외부 API 필드는 \[가설\]로 두고, 1단계에서 받은 실제 페이로드를 비식별화해 테스트 자료로 만든 뒤 확정한다.

### 8.1 Instagram (Instagram API with Instagram Login, D14)

- **방식:** Facebook 페이지 없이 Instagram 프로페셔널 계정에 직접 연결. API 호스트 graph.instagram.com, 권한 instagram\_business\_basic·instagram\_business\_manage\_messages. 개발 모드에서 앱 역할을 가진 계정으로 테스트한다.
- **검증(GET):** hub.verify\_token이 맞으면 hub.challenge 반환.
- **수신(POST) 처리 순서 (D15):**
  1. X-Hub-Signature-256으로 앱 시크릿 서명 검증. 실패 시 401.
  2. 수신 계정 ID가 세컨브레인 계정인지, 송신자 ID가 허용 목록(재후 본계정)에 있는지 확인. 아니면 저장만 하고 무시.
  3. 에코(is\_echo), 읽음·전달 등 비대상 이벤트 제외.
  4. message\_id 기준으로 webhook\_events에 저장. 이미 있으면 중복이므로 아무것도 하지 않음.
  5. 같은 트랜잭션에서 intakes와 jobs 등록.
  6. 커밋 성공 후 200. 저장 실패 시 5xx로 Meta 재전달을 유도.
- **메시지 해석:** 한 메시지에 첨부가 여럿이면 각각 접수한다. 릴스와 함께 온 텍스트는 intakes.note로 저장한다. 첨부 없는 텍스트만 질문으로 처리하고, 지원하지 않는 첨부에는 "지원하지 않는 형식이에요"로 답한다.
- **\[가설\] 릴스 첨부:** type이 ig\_reel이면 payload에 title, url, video id가 온다([Meta 변경 이력](https://developers.facebook.com/documentation/business-messaging/instagram-messaging/changelog/)). title이 전체 캡션인지, url이 영상 파일인지는 1단계에서 확인한다.
- **답장:** Send API로 24시간 응답 창 안에서만 보낸다. 보낸 답장은 기록하고, 그 에코는 3번에서 걸러 답장 루프를 막는다. HUMAN\_AGENT 예외는 자동 발송에 쓰지 않는다.

### 8.2 카카오 나에게 보내기 (보관 경로, D8)

- **전제:** 나와의 채팅 메시지는 알림이 울리지 않는다고 보고 설계한다. 1단계에서 실제 기기로 확인해 D8 결정 근거로 쓴다.
- **엔드포인트:** POST https://kapi.kakao.com/v2/api/talk/memo/default/send ([카카오 문서](https://developers.kakao.com/docs/latest/ko/message/rest-api))
- **OAuth:** 로그인 요청에 state를 넣고 콜백에서 검증한다. 연결된 카카오 사용자 ID가 재후 계정인지 확인한다.
- **토큰:** 응답의 expires\_in, refresh\_token\_expires\_in을 그대로 저장한다(고정값 금지). 갱신 응답에 새 리프레시 토큰이 없으면 기존 값을 유지한다. 갱신은 잠금으로 동시 실행을 막고, 토큰은 로그에 남기지 않으며 암호화 저장한다.
- **형식:** 리스트 템플릿은 contents가 2개 이상, 최대 3개다([기본 템플릿 문서](https://developers.kakao.com/docs/latest/ko/message-template/default)). 후보 2\~3개는 리스트, 1개는 피드 템플릿, 0개면 발송하지 않는다. 버튼으로 "전체 보기"(모바일 웹)를 단다.

### 8.3 모바일 웹

- **화면:** 검색창 + 최근 카드 / 답변 화면(답 아래 근거 팁과, 같은 엔티티·관계로 이어진 팁을 함께 표시) / 카드 상세(출처·검증 상태별 근거, 원본 릴스, 중복 후보) / 보관함(처리 상태, 실패 이유, 재시도) / 다이제스트 반응 버튼.
- **인증:** 최초 1회 비밀번호(또는 일회용 링크)로 인증한 뒤 세션 쿠키를 쓴다. URL에 장기 접근 토큰을 넣지 않고, 카드 링크에도 비밀키를 넣지 않는다.
- **답변 규칙:**
  - 근거는 저장된 팁과 주장만 쓴다. 관련 자료가 없으면 "저장한 정보에서 찾지 못했어요"라고 답하고, 모델 지식으로 빈칸을 메우지 않는다.
  - 새로 외부 조사를 하면 "저장한 정보"와 "지금 조사한 정보"를 나눠 보여준다.
  - 상충하는 팁이 있으면 상충 사실과 각각의 적용 조건을 함께 보여준다.
  - 답변과 실행 단계에 사용한 claim id를 기록한다.

| API | 메서드 | 단계 | 설명 |
| --- | --- | --- | --- |
| /webhook/instagram | GET, POST | 1 | 웹훅 검증·수신 |
| /oauth/kakao/login, /oauth/kakao/callback | GET | 1 | state 포함 카카오 연결 |
| /admin/kakao/test-send | POST | 1 | 테스트 발송 |
| /api/search | POST | 2 | 질문 → 근거 있는 답변 |
| /api/cards, /api/cards/{id} | GET | 3 | 카드 목록·상세 |
| /api/reels/{id}/retry | POST | 3 | 실패 단계부터 재처리 |
| /api/feedback | POST | 3 | 다이제스트 반응(digest\_id 포함) |

### 8.4 주간 다이제스트 선정·발송 (3단계)

캘린더·목표 정보가 없으므로 "지금 재후에게 필요하다"고 추정하지 않는다. 아래 규칙에서 나온 사유만 쓴다.

| 규칙 | 값 \[권장\] |
| --- | --- |
| 후보 | 아직 보여주지 않은 팁 / 2주 이상 지난 '나중에' 팁 / 최근 2주 질문 주제와 관련된 팁 / 오래됐지만 '관심 없음'이 아닌 팁 |
| 제외 | '관심 없음' 팁, contradicted 핵심 주장이 있는 팁, recheck\_at이 지난 팁(확인 날짜 표시 없이는 노출 금지) |
| 재노출 금지 기간 | 같은 팁 6주 |
| 발송 시각 | 매주 일요일 20:00 Asia/Seoul |
| 후보 없음 | 발송하지 않음 |
| 중복 방지 | digests에 주차 키를 고유값으로 두어 스케줄러가 다시 돌아도 한 번만 발송 |
| 실패 처리 | failed는 1회 재시도, 응답 불명은 unknown으로 두고 재발송하지 않음 |

### 8.5 질문 품질 개선 루프 (2단계)

영상에서 알렉스가 매일 쓰는 방식을 빌려, 실제 질문으로 평가셋을 키운다.

- 모든 질문과 답변, 사용한 팁·claim id를 question\_log에 저장한다.
- 답이 별로면 재후가 DM에 "별로" 또는 "이렇게 답했어야: …"라고 보낸다. 시스템은 이를 직전 질문의 피드백으로 붙인다.
- 원인을 셋 중 하나로 기록한다: 검색 누락(관련 팁을 못 찾음) / 답변 오류(찾았는데 틀리게 답함) / 지식 없음(저장된 적 없음).
- 피드백이 붙은 질문은 평가셋(9장 질문 문항)에 추가한다. 검색 방식이나 프롬프트를 고칠 때마다 전체 평가셋을 다시 돌려, 전에 맞던 질문이 깨지지 않았는지 확인한다.
- 검색 누락이 반복되면 D17에 따라 임베딩 도입을 검토한다.

### 8.6 다른 AI에서 조회 (선택, 3단계 이후)

/api/search를 감싸는 읽기 전용 MCP 서버를 두면 Claude 앱이나 Claude Code에서 "내 세컨브레인에서 찾아줘"로 바로 조회할 수 있다. 원래 요구인 '어디서든 꺼내 쓰기'에 직접 맞는다. 1인 인증 토큰을 쓰고, 8.3 답변 규칙을 그대로 적용한다.

## 9. 검증 계획과 판정 기준

검증은 1단계 기술 검증 → 2단계 품질 검증(개발용 30개 + 별도 확인용 10개) → 3단계 실사용 순서다. 추출·보강·최종 답변을 따로 채점하고, 실행을 잘못 유도하는 중대 오류는 개수와 관계없이 고친 뒤 다시 검증한다.

| 단계 | 표본 | 확인 항목 | 다음 단계 진입 기준 |
| --- | --- | --- | --- |
| 1. 기술 검증 | 릴스 5개(서로 다른 제작자, 자막형·음성형 섞기) + 카카오 테스트 발송 | 웹훅 실제 필드, URL 성격, 영상 확보, 매체별 추출, 중복 재전달 처리, 카카오 알림 여부 | 5개 중 4개 이상 영상 확보·추출. 다음 실험 진입 기준일 뿐 안정성 입증은 아님 |
| 2. 품질 검증 | 개발용 30개 + 개발에 쓰지 않은 확인용 10개 | 추출, 보강·검증, 최종 답변 | 아래 지표 충족, 중대 오류 0건 |
| 3. 실사용 | 2\~3주, 평소처럼 보내기 | 필요 발생과 해결, 다이제스트 반응 | 아래 실사용 기록으로 판단 |

### 2단계 표본 조건

유형은 겹칠 수 있다(유도형이면서 화면형일 수 있음). 30개 안에 아래 조건을 각각 최소 개수 이상 포함한다.

| 조건 | 최소 개수 | 확인할 것 |
| --- | --- | --- |
| 댓글·DM 유도형 | 10 | 미확보·AI 대안이 원본과 구분되는가 |
| 화면 글자 중심형 | 6 | 음성에 없는 핵심 정보를 잡는가 |
| 정보 충분형 | 6 | 핵심 정보가 빠짐없이 추출되는가 |
| 1년 이상 지난 릴스 | 4 | 바뀌었거나 만료된 정보를 식별하는가 |
| 비슷한 주제 묶음 | 4 | 합치지 않고 중복 후보로 정확히 연결하는가 |

### 정답표 (경량)

재후가 릴스마다 두 가지만 기록한다: 핵심 정보가 담긴 매체(음성·화면·캡션), 핵심 사실 3\~5개(중요한 숫자·조건 포함). 전체 내용을 받아쓰지 않는다.

### 품질 지표

| 구분 | 지표 | 목표 |
| --- | --- | --- |
| 추출 | 핵심 매체 확보율(정답표의 핵심 매체가 실제로 분석됐는가) | 90% 이상 |
| 추출 | 핵심 사실 포착률 | 80% 이상 |
| 보강 | 근거 일치율(evidence가 주장을 실제로 지지하는가, 재후가 표본 확인) | 90% 이상 |
| 보강 | 원본의 틀린 핵심 주장을 contradicted로 잡아낸 비율 | 측정 후 기준 설정 |
| 답변 | 아래 질문 유형별 기대 행동 충족 | 유형마다 3문항 중 3문항 |
| 전체 | 중대 오류(틀린 가격·조건·절차로 실행을 잘못 유도) | 0건. 발견 시 수정 후 확인용 10개로 재검증 |
| 비용 | 팁 1개당 처리 비용과 재후의 보정 시간 | 측정 후 기준 설정 |

### 질문 유형별 기대 행동 (유형마다 3문항, 총 18문항)

| 질문 유형 | 기대 행동 |
| --- | --- |
| 저장 자료에 정답이 있음 | 근거와 적용 조건을 함께 답변 |
| 관련 자료는 있지만 정답은 없음 | 부족함을 인정 |
| 저장 자료끼리 상충 | 상충 사실과 각각의 조건 제시 |
| 오래된 정보 | 확인 날짜와 재확인 필요 표시 |
| 저장한 적 없는 주제 | 저장한 정보에서 찾지 못했다고 답변 |
| 전체 개요("내가 뭘 모아뒀지") | 카테고리·kind별 분포와 대표 팁을 요약하고, 각 팁의 상세 링크 제시 |

### 실사용 기록

- 실제로 정보가 필요했던 순간과, 세컨브레인으로 해결한 횟수를 함께 기록한다(질문 횟수 목표는 두지 않음).
- 다이제스트에서 '유용함'을 누르고 실제로 쓴 사례(D8이 푸시 채널일 때만 재노출 효과로 해석).
- 보내기가 귀찮아 인스타 저장으로 돌아갔는지.

### 1단계 결과별 다음 결정

| 결과 | 다음 결정 |
| --- | --- |
| 영상 확보·추출이 반복해서 성공 | PRD 갱신 후 2단계 |
| 일부 제작자·형식에서만 성공 | 실패 빈도가 감수할 수준인지 판단 |
| 캡션만 확보 가능 | 영상 기반 목표에 부족함을 인정하고 수집 경로 재검토 |
| 카카오 나와의 채팅 알림 없음 확인 | 재후가 D8의 (A) 또는 (B) 선택 |

## 10. 리스크와 제약

가장 큰 리스크는 영상 확보와 재노출 채널이다. 둘 다 1단계에서 확인한다. 개인용이라도 외부 URL을 내려받고, 명령줄 도구를 실행하고, 유료 AI를 호출하므로 아래 최소 운영 계약을 구현 지시에 포함한다.

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 웹훅 URL로 영상을 못 받음 | 핵심 가치 상실 | yt-dlp 대체 경로. 그래도 실패하면 캡션만 보관하고 수집 경로 재검토 |
| 카카오 나에게 보내기 알림 없음 | 재노출 효과 검증 불가 | D8에서 재후가 선택. 구현자가 채널을 임의로 바꾸지 않음 |
| 접수 유실·중복 | 릴스 누락, 중복 답장·과금 | 영구 저장 후 200, message\_id 중복 차단, idempotency\_key(D15) |
| 원본 주장이 틀림 | 잘못된 실행 유도 | 출처와 검증 분리, 핵심 주장 외부 검증, contradicted 표시(D9, D12) |
| 근거 위조(모델이 그럴듯한 발췌·URL 생성) | 신뢰 하락 | excerpt 문자열 대조, 외부 페이지 본문 확인 후에만 저장 |
| 유사 팁 잘못 병합 | 조건이 다른 정보 손상 | 첫 버전은 병합 없이 중복 후보만(D13) |
| 비공식 다운로드의 약관 회색지대 | 개인용 한정 수용 | 원본 영상은 검증 채점 후 삭제. 삭제가 수집 방식·저작권 문제를 해소하지는 않으므로 법적 안전장치로 보지 않음 |
| 인스타 차단·사양 변경 | 다운로드 실패 증가 | 실패율 모니터링, 세컨브레인 전용 계정 사용 |
| 정보 유효기간 만료 | 바뀐 가격·조건 노출 | 확인 날짜 표시, recheck\_at 지난 팁은 다이제스트 제외. 자동 재검증은 보류 |
| 카카오 토큰 만료 | 발송 조용히 중단 | 응답의 만료값 저장, 발송 전 갱신, 실패 시 보관함 상단 안내 |
| '보내기' 습관 정착 실패 | 수집량 부족 | 실사용 기록으로 확인 |

### 최소 운영 계약 \[확정\]

| 영역 | 구현 지시 |
| --- | --- |
| 외부 URL 다운로드 | 사설·내부 주소(127.0.0.0/8, 10.0.0.0/8, 169.254.0.0/16 등)와 그쪽으로 가는 리다이렉트 차단 |
| yt-dlp·ffmpeg 실행 | 셸 문자열 조립 금지, 인자 배열로 호출, 실행 시간·파일 크기 상한 |
| 분석 자료 속 명령문 | 영상·자막·웹페이지 내용은 데이터로만 취급 |
| 웹 인증 | 최초 인증 후 세션 쿠키. URL·카드 링크에 비밀키 금지 |
| 카카오 OAuth·토큰 | state 검증, 재후 계정 확인, 토큰 암호화 저장·로그 금지, 갱신 동시 실행 잠금 |
| 비밀값 | 환경변수로만 관리, 저장소·대화창에 올리지 않음 |
| 비용 상한 \[권장\] | 릴스당 프레임 최대 60장, 외부 검색 최대 5회, 단계별 재시도 최대 3회, 일일 예산 상한 초과 시 작업 대기 |
| 실패 노출 | 보관함에 실패 단계·이유·재시도 버튼 |
| 재처리 추적 | 추출기·모델·프롬프트 버전과 처리 이력을 processing\_runs에 보존 |
| 원본 영상 보존 | 2단계 채점이 끝날 때까지 보존(video\_delete\_after), 이후 삭제. 임시 프레임·오디오는 작업 종료 시 정리 |

## 11. 구현 로드맵

공통 스키마와 모듈 입출력을 먼저 확정한 뒤에만 병렬 구현한다. 1단계-A는 재후의 계정 준비 없이 코드부터 시작할 수 있다.

### 단계별 작업

1. **1단계-A · 코드 준비 (계정 불필요)**
   - Claude Code: 저장소 구조, 1단계 테이블(6장), jobs 워커, 웹훅 서버(서명·송신자 확인·영구 저장·200 순서), 카카오 OAuth 콜백·토큰 관리
   - Codex: 영상 확보 모듈(SSRF 차단·인자 배열·상한), 프레임 샘플링·OCR, Whisper 전사. 로컬 영상 파일로 테스트
   - 테스트: Meta 문서 예시 페이로드로 만든 모의 테스트(서명 실패, 비허용 송신자, 에코, 같은 message\_id 재전달, 첨부 여러 개)
2. **1단계-B · 실계정 연동 (재후 준비 후)**
   - 서버 배포 → Meta 웹훅 GET 검증 → 릴스 5개 전송
   - 실제 페이로드를 비식별화해 tests/fixtures에 저장
   - 카카오 로그인·테스트 발송, 실제 기기 알림 확인
   - 게이트: 9장 1단계 기준. 재후가 D8 선택
3. **PRD 갱신 (Claude Code 단독)**
   - 실제 필드로 \[가설\] 항목 확정, 지식 계층 DDL·오류 규격·모듈 입출력 확정
4. **2단계 · 모듈 구현 (스키마 확정 후 병렬)**
   - Claude Code: 팁 분해 → 근거 대조 → 판별 → 보강·검증 파이프라인 통합
   - Codex: 검색 API와 답변 규칙, 중복 후보 연결, LLM 출력 계약 검증 테스트
5. **2단계 · 통합 검증**
   - 개발용 30개 채점 → 수정 → 확인용 10개로 최종 확인
6. **3단계 · 모바일 웹·다이제스트 → 2\~3주 실사용**

### 협업 규칙

| 항목 | 규칙 |
| --- | --- |
| 작업 공간 | 같은 저장소에서 에이전트별 git worktree와 작업 브랜치 사용 |
| 공통 스키마 | 마이그레이션·공통 타입 변경은 Claude Code만 하고, Codex는 변경 요청을 남김 |
| 리뷰 | 각자 상대의 PR을 교차 리뷰 |
| 테스트 보고 | '모의 테스트 통과'와 '실계정 연동 성공'을 반드시 구분해 보고 |
| 지시 파일 | 이 문서를 docs/PRD.md로 두고, CLAUDE.md·AGENTS.md에 "PRD.md의 D1\~D17과 10장 최소 운영 계약을 따른다. \[가설\] 항목은 확정 계약처럼 구현하지 않는다. 현재 범위는 1단계뿐이다"를 명시 |

## 13. 보류 항목과 향후 확장

아래 항목은 요구로는 유효하지만 PoC에서는 뺀다. 실사용에서 필요가 확인될 때 이 순서대로 검토한다.

| 항목 | 보류 이유 | 재검토 조건 |
| --- | --- | --- |
| 과거 저장 목록 가져오기 | 핵심 흐름 검증이 먼저 | 2단계 통과 후(D5). 실제 파일 샘플로 파서 작성, 재가져오기 중복 검사 |
| 받은 노션 링크·파일 연결 | 어느 팁의 자료인지 연결하는 흐름과 파일 처리 설계가 필요 | 실사용 중 유도형 자료를 실제로 받는 일이 반복될 때 |
| 유사 팁 자동 병합 | 조건이 다른 정보 손상 위험(D13) | 중복 후보의 사람 판정 데이터가 쌓여 정확도를 측정할 수 있을 때 |
| 자동 재검증 | 누가 언제 확인하고 실패를 어떻게 표시할지 미설계 | 바뀌는 정보 비중이 크다고 확인될 때. 그전에는 확인 날짜 표시만 |
| 주고받은 DM 속 릴스 수집 | 자동 동기화 불가, 대용량 내보내기, 제3자 개인정보 | "보낸·받은 릴스를 찾고 싶다" 요구가 반복될 때. 기본은 링크·시각·방향만, 대화 맥락은 선택. 상대방 대화가 일반 검색에 섞이지 않게 분리 |
| 상황 기반 추천(목표·캘린더·위치) | 목표 등록은 숙제가 되고, 일정만으로 의도 추정이 부정확 | 다이제스트만으로 "잊는 문제"가 남을 때, 명시적 동의 후 |
| Obsidian 연결 | 처리 시스템이 아니라 열람·편집 계층 | 실사용 후 원하면 마크다운 내보내기. 사람이 고친 내용은 덮어쓰지 않는 규칙 필수 |
| 그래프 화면·그래프 DB | 보기는 좋지만 잘 열지 않음 | 관계 테이블로 시작, 관계 탐색 필요가 확인될 때 |
| 네이티브 앱 | 인스타 공유도 URL만 전달, DM 경로와 차이 없음 | 서비스화 결정 이후 |
| 배우자 공용 사용 | 1인 판정 기준 유지 | PoC 통과 후, 사용자별 보관함 분리와 함께 |
| 서비스화(다른 사용자) | 비공식 다운로드 불가, 앱 게시 전 비즈니스 인증·심사·개인정보 처리 필요. 비밀번호·세션 쿠키 수집 설계 금지 | 별도 기획. 공식 경로만으로 영상 확보가 가능한지가 선결 조건 |
| 주제 페이지(여러 팁을 엮은 파생 요약) | LLM 위키의 핵심이지만, 자동 병합과 같은 정보 손상 위험이 있고 팁이 적을 때는 효용이 낮음 | 팁이 100개 이상이고 같은 주제 질문이 반복될 때. 팁을 인용만 하고 원본 팁은 그대로 둠 |
| 좋은 답변을 지식으로 보관 | 모델이 합성한 답변이 원본처럼 쌓이는 위험 | 재후가 직접 '저장'을 누른 답변만, 별도 유형(답변 노트)과 claim 인용을 유지한 채로 |
